\chapter{Robot Platform and Integration}
\label{cap:platform}

This chapter describes the robot used in the field tests, the software that runs on it, and the deployment of the segmentation network.

\section{Robot hardware and sensors}
\label{sec:hardware}

\subsection{Robot platform}
\label{subsec:robot_platform}

The experimental platform is Demetra, a mobile robot prototype developed by the Roboto student team of the Politecnico di Torino. It has four-wheel steering (4WS) and four-wheel drive (4WD).

Each wheel has a DJI RoboMaster M3508 brushless motor with a DJI RoboMaster C620 speed controller, and its own CubeMars AK70-10 actuator for steering. A DJI RoboMaster Development Board Type C (STM32F407) controls the speed controllers and the steering actuators. It receives the linear velocity and the steering angle from the onboard computer and sends back the measured platform speed and steering angle. The wheelbase is $L = 40$~cm, the track width is $T = 34$~cm, the wheel diameter is 19~cm ($r_w = 9.5$~cm) and the chassis is 15~cm above the ground.

\begin{figure}[!t]
  \centering
  \includegraphics[width=0.85\linewidth]{images/platform/demetra_side.png}
  \caption{Side view of Demetra, with the wheel diameter, the wheelbase $L$, the camera height $h_{\mathrm{cam}}$ and the adjustable tilt $\theta$ of the camera.}
  \label{fig:robot_camera_setup}

Steering is described by a kinematic bicycle model with opposite-phase steering (Figure~\ref{fig:c7_kinematics}), where the equivalent front and rear steering angles are $\delta_f=\delta$ and $\delta_r=-\delta$. With pure rolling, the turning radius of the mid-axle point $M$ is
\begin{equation}
    R = \frac{L}{2 \tan\delta}.
    \label{eq:turning_radius_4ws}
\end{equation}

\end{figure}

\subsection{Camera configuration}
\label{subsec:camera}

The camera is an Intel RealSense D435, mounted on the front of the robot frame on a mount with adjustable tilt (Figure~\ref{fig:robot_camera_setup}). The color stream is used at $640 \times 480$ pixels and 30 frames per second. The camera is tilted downward by a few degrees, so that the image shows mainly the path, which covers about the lower 70\% of the image, as the region of interest of the extractors. The tilt is adjusted to the field.

\subsection{Computing platform}
\label{subsec:computing}

The onboard computer is an NVIDIA Jetson AGX Orin Developer Kit (64~GB), with a 12-core ARM Cortex-A78AE CPU and an NVIDIA Ampere GPU with 2048 CUDA cores. It runs Ubuntu 22.04 with L4T R36.4.4. The software runs in a Docker container with access to the GPU and to the USB devices. Inside the container, ROS~2 Humble runs the camera driver, the controller node, and the serial driver.

\section{Software architecture}
\label{sec:software}

\subsection{ROS integration}
\label{subsec:ros}

The software pipeline is implemented in ROS~2. Figure~\ref{fig:ros2_architecture} shows the node graph of the robot. Three nodes are active. The RealSense node (\texttt{/camera/camera}) publishes the compressed color images. The controller node (\texttt{/controller\_node}) subscribes to these images. In the same callback, it runs the segmentation network and the path extractor, computes the velocity command (Section~\ref{subsubsec:control_node}), and publishes it on \texttt{/cmd\_vel}. The serial driver node (\texttt{/demetra\_node}) receives the commands and sends them to the microcontroller. The controller node also publishes debug topics under \texttt{/debug}, which are used during configuration and are omitted from the figure. When the debug video is enabled, it also publishes three debug images (segmentation, region of interest and path), shown in Figure~\ref{fig:debug_video}. The debug video makes the node skip camera frames (Section~\ref{subsec:timing}), so it should be disabled when the robot operates. The text log on \texttt{/debug/text} is always active. It carries important information on each frame and its cost is small, so the node still processes every camera frame.

The image subscription keeps only the last frame, so frames that arrive during the processing are not queued and the controller always processes the most recent image seen by the robot.

\subsection{Control interface}
\label{subsec:control_interface}

The serial driver node (\texttt{/demetra\_node}) converts each command $(v, \omega)$ into the steering angle
\begin{equation}
    \delta = \arctan\left(\frac{L\, \omega}{2\, v}\right),
    \label{eq:4ws_steering_angle}
\end{equation}
limited to $\pm 30^\circ$. Before the conversion, the node limits $v$ to $\pm 1.5$~m/s and $\omega$ to $\pm 6.0$~rad/s. Every 10~ms it sends the last $v$ and $\delta$ to the microcontroller. If no command arrives for 500~ms, it sets the speed to zero.

\begingroup\color{red}
The microcontroller computes the steering angle of each wheel and the wheel speeds. For track width $T$ and turning radius $R = L / (2\tan\delta)$, the left and right steering angles follow the dual-Ackermann geometry:
\begin{equation}
    \delta_{L} = \arctan\left(\frac{L/2}{R - T/2}\right), \qquad
    \delta_{R} = \arctan\left(\frac{L/2}{R + T/2}\right),
    \label{eq:ackermann_4ws}
\end{equation}
with $\delta_{FL} = \delta_L$, $\delta_{FR} = \delta_R$, $\delta_{RL} = -\delta_L$, and $\delta_{RR} = -\delta_R$. The linear velocity of each wheel $i \in \{FL, FR, RL, RR\}$ is
\begin{equation}
    v_i = \omega \sqrt{\left(\frac{L}{2}\right)^2 + R_i^2},
    \label{eq:wheel_velocity}
\end{equation}
where $R_i$ is the lateral distance from the ICR to the wheel center plane. The wheel speeds $v_i / r_w$ are converted into motor speed setpoints through the 19:1 gear ratio.
\endgroup

\subsection{Controller node}
\label{subsubsec:control_node}

For each frame, the controller node decodes the image, resizes it to $224\times224$ pixels and normalizes it with the ImageNet mean and standard deviation. The segmentation network turns the image into the label mask, and the path extractor (Chapter~\ref{cap:geometric_reference}) turns the mask into a centerline.

The lateral error $e$ is the horizontal offset, in pixels, of the centerline from the image center at row $y_{\mathrm{ref}} = 156$ of the $W \times H = 224\times224$ input. It is positive when the centerline is on the right. The error then passes through a filter that depends on the status returned by the path extractor (Section~\ref{sec:c6_output}), a deadband and the steering law, which gives the angular velocity command.

\paragraph{Error filter.}
The error is smoothed with an exponential moving average (EMA). At each frame $k$, the filtered error is a weighted average of the previous filtered error $\hat{e}_{k-1}$ and of the new measurement $e_k$:
\begin{equation}
    \hat{e}_k = (1 - \alpha)\, \hat{e}_{k-1} + \alpha \, e_k.
    \label{eq:filter_ema_update}
\end{equation}
The smoothing factor $\alpha$ is the weight of the new value. With $\alpha = 0.20$ the filter keeps 80\% of the previous value at each frame, so after three frames it has covered about half of a step of the input and after about 13 frames 95\% of it. At 30 frames per second this takes 0.1~s and 0.45~s. The angular velocity sent to the robot is smoothed in the same way.

\paragraph{Smoothing independent of the frame rate.}
If the node runs slower, the same three frames last longer and the filter reacts later. With the debug video enabled, for example, the node processes 17 to 24 frames per second (Section~\ref{subsec:timing}). The smoothing factors are therefore defined as reference values $\alpha_{\mathrm{ref}}$ for 30 frames per second. At each frame, the node measures the time $\Delta t$ since the previous frame, limited to the interval from $1/120$ to $0.25$~s, and converts each reference factor into
\begin{equation}
    \alpha = 1 - (1 - \alpha_{\mathrm{ref}})^{30\,\Delta t}.
    \label{eq:alpha_dt}
\end{equation}
With $\Delta t = 1/30$~s, $\alpha = \alpha_{\mathrm{ref}}$. At 15 frames per second, for example, $\alpha_{\mathrm{ref}} = 0.20$ gives $\alpha = 1 - 0.8^{2} = 0.36$, so the filter keeps 64\% of the previous value at each frame, as in two frames at 30 frames per second. The filter therefore follows the same response in time, only with fewer updates (Table~\ref{tab:ema_frame_rate}). Figure~\ref{fig:ema_frame_rate} shows the two responses.

\paragraph{Parameters per status and jumps.}
When the status is \texttt{ok} or \texttt{degraded}, the filter updates the error with a reference smoothing factor $\alpha_{\mathrm{ref}}$ and a jump threshold $J$ that depend on the status:
\begin{equation}
    (\alpha_{\mathrm{ref}}, J) =
    \begin{cases}
        (0.20, \; 40\text{ px}) & \text{if the status is \texttt{ok}}, \\
        (0.18, \; 38\text{ px}) & \text{if the status is \texttt{degraded}}.
    \end{cases}
    \label{eq:filter_regimes}
\end{equation}
In our case the values for the two statuses are close to each other and worked well. The filter keeps them separate, so that the values for \texttt{degraded} can be changed if the segmentation is worse. When the status is \texttt{lost}, the error is not updated and the robot stops after a short hold, described at the end of this section.

The jump is the distance $\Delta_k = |e_k - \hat{e}_{k-1}|$ between the new measurement and the previous filtered error. The filtered error is
\begin{equation}
    \hat{e}_k =
    \begin{cases}
        (1 - \alpha)\, \hat{e}_{k-1} + \alpha \, e_k & \text{if } \Delta_k \le J, \\
        e_k & \text{if } \Delta_k > J,\ \Delta_{k-1} > J \text{ and } |e_k - e_{k-1}| \le J_c, \\
        \hat{e}_{k-1} & \text{otherwise}.
    \end{cases}
    \label{eq:filter_jump}
\end{equation}
A measurement within the threshold is smoothed with Equation~\eqref{eq:filter_ema_update}. A jump on an isolated frame is ignored, so a segmentation error on a single frame does not reach the command. A jump present in two consecutive frames is taken directly only if the two measurements agree, that is, if they differ by at most the tolerance $J_c$. Otherwise both frames are ignored.

We chose $J_c$ from the raw errors recorded during the field runs with Strip-IRLS (Section~\ref{sec:field_validation}). When a jump lasted two frames, the two measurements were either within 18~px of each other or more than 50~px apart. In the first case the two frames agree on the new position of the centerline. In the second case they place it in two different positions, so at least one of them is an error. $J_c = 25$~px accepts the first case and rejects the second.

\paragraph{Steering law.}
The steering law uses the command error
\begin{equation}
    e_{\mathrm{cmd}} =
    \begin{cases}
        0 & \text{if } |\hat{e}_k| < 4\text{ px}, \\
        \hat{e}_k & \text{otherwise}.
    \end{cases}
    \label{eq:deadband}
\end{equation}
This deadband avoids small oscillations of the steering around the center of the row. It acts only on the command, so the filter keeps its internal value $\hat{e}_k$. The angular velocity target is
\begin{equation}
    \omega^{*} = - K_{p} \, (0.6 + 0.4\, C) \, \frac{e_{\mathrm{cmd}}}{W/2},
    \label{eq:control_law_omega}
\end{equation}
with $K_{p} = 1.2$. Dividing by the half-width $W/2 = 112$~px gives the error as a fraction of the image, from 0 at the center to $\pm 1$ at the edges, so $K_p$ does not depend on the input resolution. The confidence $C \in [0, 1]$ of the path extractor reduces the gain when the result is less reliable. With $C = 1$ the full gain $K_p$ is used, and with $C = 0.38$, the lowest value before \texttt{lost}, about 75\% of it. The minus sign makes the robot turn towards the centerline. The controller limits the value to $\pm\omega_{\max} = \pm 0.58$~rad/s. This limit is chosen from $v$ so that it matches the steering limit of $30^\circ$ (Equation~\eqref{eq:4ws_steering_angle}): a larger $\omega$ would not turn the wheels further. The command therefore saturates for errors above
\begin{equation}
    e_{\mathrm{sat}} = \frac{\omega_{\max}\, (W/2)}{K_p\, (0.6 + 0.4\, C)},
    \label{eq:error_saturation}
\end{equation}
which is about 54~px with $C = 1$ (Figure~\ref{fig:steering_law}a). The gain $K_p$ sets how strongly the robot reacts to the error (Figure~\ref{fig:steering_law}b). A larger $K_p$ gives a larger command for the same error and reaches $30^\circ$ at a smaller error. A smaller $K_p$ gives a smoother response and reaches the limit later. A second EMA smooths the angular velocity sent to the robot, $\omega_k = (1 - \alpha_w)\,\omega_{k-1} + \alpha_w\,\omega^{*}$, with $\alpha_w = 0.30$ at 30 frames per second (converted with Equation~\eqref{eq:alpha_dt}, so this filter is also independent of the frame rate). The linear velocity is constant, $v = 0.20$~m/s.

The values of $K_p$ and $\omega_{\max}$ above hold for $v = 0.20$~m/s. The steering angle of Equation~\eqref{eq:4ws_steering_angle} depends on the ratio $\omega / v$, so at a higher speed the same $\omega$ turns the wheels less. If only $v$ is increased, the robot steers less for the same error. At $v = 0.50$~m/s, for example, $\omega_{\max} = 0.58$~rad/s gives at most $13^\circ$. To keep the same steering angle for each error at a different speed, $\omega_{\max}$ and $K_p$ should be multiplied by the same factor as $v$:
\begin{equation}
    \omega_{\max} = \frac{2\, v \tan 30^\circ}{L} \approx 2.89\, v, \qquad K_p = 1.2\, \frac{v}{0.20~\text{m/s}}.
    \label{eq:speed_scaling}
\end{equation}
In this way $\omega_{\max}$ still corresponds to $30^\circ$ and each error gives the same steering angle as at 0.20~m/s. At $v = 0.30$~m/s, for example, $\omega_{\max} = 0.87$~rad/s and $K_p = 1.8$.

\paragraph{Missing centerline and stop.}
When the status is \texttt{lost} or no centerline is available, the node keeps the last filtered error for up to $t_{\mathrm{hold}} = 0.5$~s. After this time it publishes a zero velocity command. After a stop, the error filter restarts from the first new measurement and the filter of the angular velocity from zero. Table~\ref{tab:controller_parameters} lists the parameters used on the robot.

\section{Deployment and testing}
\label{sec:deployment}

\subsection{Timing and latency}
\label{subsec:timing}

The inference times in Table~\ref{tab:c5_architecture_results} were measured on the training GPU at the original image resolution, so they do not describe the onboard model. The times in this section were measured on the Jetson AGX Orin in the MAXN power mode, with the clock frequencies fixed at their maximum by \texttt{jetson\_clocks}, so that the runs are comparable. For each path extractor, the controller node processed the same recording of a row, played at its original speed, once with the debug video disabled and once with it enabled. For each run, 100 callbacks were measured. Table~\ref{tab:jetson_extractors} lists the mean and standard deviation of the time of the path extractor and of the whole callback.

Without the debug video, the callback takes from 11.3~ms with Column histogram to 26.2~ms with RANSAC edges, less than the 33.3~ms frame period of the camera. The node therefore processes every camera frame, and at $v=0.20$~m/s the robot moves about 0.67~cm between two processed frames. The debug video adds 29 to 33~ms, and every callback becomes longer than the frame period. The node then processes 17 to 24 frames per second and skips the others, so the robot moves 0.8 to 1.2~cm between two processed frames. The smoothing factors are corrected for the time between frames (Equation~\eqref{eq:alpha_dt}), so the response of the filters in time does not change. The difference between the two cases is small, so the field tests of Chapter~\ref{cap:experiments} were run with the debug video enabled, to record the debug images. In normal operation it should still be disabled, so that every frame is used.

\subsection{Software-in-the-Loop test}
\label{subsec:sitl}

Before the field tests, the complete pipeline was tested in the laboratory with the robot raised, so that the wheels could steer without moving the robot. A simulation node replaces the camera. It publishes a recorded frame of a row on the camera topic at 30 frames per second, and the controller node runs on these frames without changes. The simulation node keeps a lateral offset and a heading of a simulated robot, updates them from the velocity commands with the steering model of the driver (Equation~\eqref{eq:4ws_steering_angle}), and shifts the frame horizontally by the corresponding number of pixels. During the test, the image is shifted from the keyboard, which moves the simulated robot to either side of the row. Figure~\ref{fig:sitl_test} shows three frames of the test.

The test checks that the commands computed from the images are correct: after each displacement, the wheels steered towards the center of the row and the simulated offset returned to the center without oscillating. It is not a verification of the stability of the closed loop, because the scene is a single shifted frame and the projection is approximate. The network segments every frame, but always the same image shifted laterally. The segmentation and the path extraction along a real row were instead tested by playing recordings of the rows to the controller node, as in Section~\ref{subsec:timing}.
